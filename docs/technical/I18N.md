# Internationalization (i18n) Guide

This document explains how translations work in Balados Sync, how to add new translated strings, and the conventions to follow.

## Overview

Balados Sync uses [Gettext](https://hexdocs.pm/gettext/) for internationalization. Gettext is Elixir's standard i18n library, based on the GNU gettext system.

**Supported locales:** `fr` (French, default), `en` (English)

**Locale resolution** is handled by `BaladosSyncWeb.Plugs.Locale` and differs depending on the pipeline:

| Priority | Browser (`:browser` pipeline) | API (`:api` pipeline) |
|----------|-------------------------------|------------------------|
| 1 | `?locale=` query parameter | `?locale=` query parameter |
| 2 | Session (persisted from previous request) | *(no session)* |
| 3 | `Accept-Language` header | `Accept-Language` header |
| 4 | Default locale (`fr`) | Default locale (`fr`) |

## File Structure

```
apps/balados_sync_web/priv/gettext/
  default.pot                         # Template (source of truth for msgids)
  errors.pot                          # Template for Ecto/validation errors
  fr/LC_MESSAGES/
    default.po                        # French translations
    errors.po                         # French error translations
  en/LC_MESSAGES/
    default.po                        # English translations
    errors.po                         # English error translations
```

- **`.pot` files** (PO Templates) are auto-generated. Do not edit translations there.
- **`.po` files** contain the actual translations per locale. Edit these.

## How to Add a New Translation

### Step 1: Use `gettext` in your code

In controllers, views, or templates:

```elixir
# In a module (controller, plug, etc.)
use Gettext, backend: BaladosSyncWeb.Gettext

# Simple translation
gettext("auth.unauthorized")

# With interpolation
gettext("subscriptions.count", count: 5)

# Domain-specific (e.g., error messages)
dgettext("errors", "can't be blank")

# Plural forms
ngettext("1 podcast", "%{count} podcasts", count)
```

In HEEx templates:

```heex
<p><%= gettext("dashboard.welcome") %></p>
<p><%= ngettext("1 item", "%{count} items", @count) %></p>
```

### Step 2: Extract keys

Run the extraction command to update `.pot` template files:

```bash
cd apps/balados_sync_web
mix gettext.extract
```

This scans all source files for `gettext/1`, `dgettext/2`, `ngettext/3`, etc. and updates the `.pot` files with any new `msgid` entries.

### Step 3: Merge into locale files

```bash
mix gettext.merge priv/gettext
```

This propagates new `msgid` entries from `.pot` files into each locale's `.po` files. New entries will have empty `msgstr` values that need to be filled in.

### Step 4: Translate

Edit the `.po` files for each locale:

```
# priv/gettext/fr/LC_MESSAGES/default.po
msgid "auth.unauthorized"
msgstr "Non autorise"

# priv/gettext/en/LC_MESSAGES/default.po
msgid "auth.unauthorized"
msgstr "Unauthorized"
```

### One-liner for extract + merge

```bash
cd apps/balados_sync_web && mix gettext.extract --merge
```

## Naming Conventions

Translation keys use **dot-separated namespaces** matching the feature area:

| Prefix | Usage | Examples |
|--------|-------|----------|
| `auth.*` | Authentication & authorization | `auth.unauthorized`, `auth.logged_out` |
| `subscriptions.*` | Subscription management | `subscriptions.subscribed`, `subscriptions.already_subscribed` |
| `import_opml.*` | OPML import feature | `import_opml.success`, `import_opml.parse_error` |
| `setup.*` | Initial server setup | `setup.welcome_admin`, `setup.already_configured` |
| `feed_page.*` | Public feed pages | `feed_page.not_found` |
| `errors.*` | Validation errors (use `dgettext("errors", ...)`) | `can't be blank`, `is invalid` |

### Rules

1. **Always use dotted keys**, not full English sentences (e.g., `auth.unauthorized` not `"You are not authorized"`).
2. **Group by feature**, not by page or component.
3. **Keep keys stable** -- renaming a key breaks all locale files.
4. **Use interpolation** for dynamic values: `gettext("import_opml.count", count: n)` with `msgid` containing `%{count}`.

## API Locale Support

The `:api` pipeline includes the `Locale` plug, so API error messages are translated based on the client's `Accept-Language` header or `?locale=` query parameter.

### Example: API client requesting French error messages

```bash
curl -H "Accept-Language: fr" https://server/api/v1/subscriptions
# Error messages will be in French

curl "https://server/api/v1/subscriptions?locale=en"
# Error messages will be in English
```

Since API requests are stateless (no session), the locale is determined fresh on each request. The query parameter always takes priority over the header.

## Testing with Locales

The test environment uses English as the default locale (configured in `config/test.exs`):

```elixir
config :balados_sync_web, default_locale: "en"
```

The `ConnCase` setup also explicitly sets the Gettext locale to `"en"` so that test assertions can match English strings consistently.

To test locale-specific behavior, override the locale in your test:

```elixir
test "returns French error message", %{conn: conn} do
  conn =
    conn
    |> put_req_header("accept-language", "fr")
    |> get("/api/v1/some-endpoint")

  assert json_response(conn, 401)["message"] =~ "autorise"
end
```

## Adding a New Locale

1. Create the locale directory and PO files:
   ```bash
   mkdir -p apps/balados_sync_web/priv/gettext/es/LC_MESSAGES
   ```

2. Add the locale to the supported list in `BaladosSyncWeb.Plugs.Locale`:
   ```elixir
   @supported_locales ["fr", "en", "es"]
   ```

3. Run extraction and merge:
   ```bash
   cd apps/balados_sync_web && mix gettext.extract --merge
   ```

4. Translate all `msgstr` values in the new `.po` files.

5. Add tests for the new locale in `locale_test.exs`.
